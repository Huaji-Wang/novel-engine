# novel-engine

**[English](./README.md)**

**面向长篇叙事的本地优先多智能体写作引擎。**

`novel-engine` 是一套开源、可在本机运行的写作系统，面向**长篇小说、连载与网文**。

它不会试图用一次提示词生成整本书。

它用**多阶段、多智能体**流程，把最初的想法做成会生长的故事结构，再按**一条弧、一份细纲、一章正文**往下写。

你始终是作者，也是最终拍板的人。
AI 负责规划、起草、修订、连续性与状态追踪。

> **在本地规划。按增量写。故事始终由你掌控。**

- **作者：** [Huaji-Wang](https://github.com/Huaji-Wang)
- **许可证：** [AGPL-3.0](./LICENSE)
- **云端版本：** 规划中

> **clone 之前先知道：** 界面与内置提示词目前**只有中文**，引擎也是按中文行文调的。
> 英文界面与英文提示词在路线图上，但现在还不存在。

## 为什么需要 novel-engine？

长篇写作并不是对大模型说一句「写本小说」就够了。

模型可以写出像样的一段。更难的是让它：

- 记得五十章以前发生过什么；
- 维持前后一致的角色状态；
- 守住世界观规则；
- 管住拖得很长的故事弧；
- 在各章之间稳住节奏；
- 埋下伏笔并在之后兑现；
- 在作者改了前面的决定时跟着调整；
- 避免把整本书压成一份再也动不了的死大纲。

`novel-engine` 把长篇生成当成**持续规划与状态管理问题**，而不是一次性生成任务。

因此写作过程被拆成多个阶段：

```text
Idea
  │
  ▼
Co-Creation
  │
  ▼
Story Blueprint
  │
  ├── Core Seed
  ├── Characters
  ├── World
  ├── Arc Structure
  └── Long-term Direction
  │
  ▼
Chapter Outline
  │
  ▼
Chapter Draft
  │
  ├── Revision
  ├── Polishing
  └── AI-assisted Rewriting
  │
  ▼
Author Approval
  │
  ▼
Story State Update
  │
  ├── Summary
  ├── Character State
  ├── World State
  ├── Foreshadowing
  └── Continuity Records
  │
  ▼
Next Chapter
```

真正要紧的是这个循环：

**写 → 改 → 认可 → 更新状态 → 继续**

故事不会被当成一份静止的提示词。

## 核心理念

### 1. 不要一次生成整本小说

长篇天然不确定。

`novel-engine` 不会强迫模型在写第一章之前就把全书情节钉死，而是采用**渐进规划**。

现在需要的部分详细规划；更远的方向只保留较软的指引。

例如：

```text
Whole Novel
    │
    └── Long-term direction
            │
            └── Current Arc
                    │
                    ├── Chapter 1
                    ├── Chapter 2
                    ├── Chapter 3
                    └── ...
```

当前弧得到较细的规划。

全书其余部分有意保持弹性。

这样改方向时，不必立刻把整本书作废。

---

### 2. 作者始终在环里

`novel-engine` 不是用来取代作者的。

几乎每个关键阶段你都可以插手：

- 改最初的创意；
- 规划前先和 AI 讨论故事；
- 编辑蓝图；
- 改章节细纲；
- 给某一章额外指令；
- 重写选中的片段；
- 修订生成的章节；
- 确认或拒绝新冒出来的角色与设定；
- 改全局写作指导；
- 在你有意推倒重来时重新生成规划。

AI 给出建议和草稿。

**什么算进正史，由作者决定。**

---

### 3. 记忆是结构化状态，不是无限加长的上下文窗口

长篇很快就会超出「整段对话里塞得下」的范围。

`novel-engine` 不会把全书手稿反复塞进每一次提示，而是维护结构化的故事状态。

例如：

- 章节摘要；
- 角色状态；
- 世界观信息；
- 未收束的线索；
- 伏笔；
- 故事进展；
- 已确认与未确认的实体。

后面的章可以取用**真正需要的信息**，而不是把整部小说历史重放一遍。

## 多智能体工作流

长篇写作的不同环节，应由不同专长的角色来做。

而不是让同一个智能体同时充当：

> 小说家 + 策划 + 编辑 + 连续性检查 + 记忆管理员

流程把这些职责拆到不同阶段、不同智能体。

一次典型的生成循环如下：

```text
                  ┌─────────────────┐
                  │   Author Idea   │
                  └────────┬────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │  Co-Creation    │
                  │     Agent       │
                  └────────┬────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │ Blueprint /     │
                  │ Planning Agents │
                  └────────┬────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │ Outline Agent   │
                  └────────┬────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │ Writing Agent   │
                  └────────┬────────┘
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
          ┌──────────────┐   ┌──────────────┐
          │ Revision /   │   │ Continuity / │
          │ Polish Agent │   │ Quality Check│
          └──────┬───────┘   └──────┬───────┘
                 │                  │
                 └────────┬─────────┘
                          ▼
                 ┌─────────────────┐
                 │  Author Review  │
                 └────────┬────────┘
                          │
                          ▼
                 ┌─────────────────┐
                 │ Story State     │
                 │ Update          │
                 └────────┬────────┘
                          │
                          └──────► Next Chapter
```

具体有哪些智能体，会随项目发展调整。

要紧的原则是**分工，以及受控的信息流动**，而不是单纯把智能体堆得更多。

## 从想法到第一章

启动本地应用后，新建一本书并提供：

- 书名；
- 故事创意；
- 可选的类型信息；
- 可选的同人模式。

然后可以进入**开书共创（Co-Creation）**。

### 开书共创

不必把一句话创意立刻变成完整大纲。你可以先和 AI 讨论前提。

对话会逐渐整理成结构化的**创作指令草稿（Creative Instruction Draft）**。

这份文档是后续规划的基础。

确认之前，你可以反复改、反复聊。

---

### 蓝图

创作方向确认后，系统生成蓝图，通常包括：

- 故事核心种子；
- 人物与关系；
- 世界观；
- 当前弧结构；
- 长期故事方向；
- 最初几章细纲。

关键区别是：系统**不会**试图把整本书一次性锁死。

第 1 弧得到相对细致的规划。

最终结局被当成**弱指南针（soft compass）**，而不是一纸合同。

---

### 章节细纲

每一章会有更细的细纲，描述打算怎么走节拍。

作者可以：

- 手工改细纲；
- 让 AI 修订；
- 必要时重新生成。

细纲是高层规划与真正写正文之间的桥。

---

### 章节生成

细纲就绪后，写作智能体生成该章。

你可以给**这一章**额外指令；全局写作指导则另存、长期生效。

生成后的章节可以：

- 修订；
- 润色；
- 「去 AI 味」；
- 局部重写；
- 做质量与一致性检查。

在作者**定稿（finalize）**之前，这些都不会进入官方故事状态。

---

## 定稿与故事状态

定稿是 `novel-engine` 里的重要概念。

生成出来的章节不会自动算作正史。

你认可一章之后，系统才更新持久的故事状态。

例如：

```text
Chapter 12
    │
    ▼
Author Approval
    │
    ├── Chapter Summary
    ├── Character Changes
    ├── New Characters
    ├── World Changes
    ├── Foreshadowing
    └── Other Story State
            │
            ▼
       Global Memory
            │
            ▼
       Chapter 13
```

这样就划清了：

**AI 建议过什么**

和

**小说里真正发生了什么。**

写作中新发现的角色或设定，也可以停在**待确认（pending）**，直到作者点头。

---

## 长篇连续性

长篇一定会堆信息。

因此 `novel-engine` 维护多种结构化状态，包括：

### 角色状态

追踪故事进行中会变的信息，而不是把角色卡当成永远不变的说明书。

### 世界状态

保存后面章节可能必须遵守的重要世界观信息。

### 伏笔

追踪尚未收束的叙事元件，降低写了几十章之后被忘掉的概率。

### 章节摘要

用压缩后的前文代表已发生的事，而不是每次生成都把全书正文再塞一遍。

### 待确认状态

新实体与新事实可以标成 **pending**，直到作者确认它们是否进入正史。

---

## 为连载／网文而设计

`novel-engine` 特别关心**连载／网文**的工作方式。

系统会显式考虑：

- 章级节奏；
- 章末钩子；
- 故事弧；
- 推进；
- 长线伏笔；
- 反复出场的人物；
- 连续性；
- 增量规划。

一章不只回答：

> 「接下来发生了什么？」

还要考虑：

> 「读者为什么要翻下一章？」

---

## 同人模式

`novel-engine` 提供专门的**同人模式**。

共创确认后，相关字段可以锁得更严，生成内容就不那么容易随手打破原作约束。

目标不是完美复刻原作者文风。

重点是守住：

- 角色身份；
- 已有关系；
- 世界规则；
- 原作边界；
- 用户自己定的限制。

## 它是什么——以及不是什么

### 它是

- **本地优先**的长篇写作环境。
- **多智能体**写作流程。
- 结构化的规划与生成系统。
- 人机共创工具。
- 围绕按章增量生成来设计。
- 把故事状态与连续性管理放在设计中心。
- 方便换不同 LLM 提供商做实验。

### 它不是

- 一键「生成整本小说」的按钮。
- 只能上云的 SaaS。
- 写第一章前必须订死全书结局的系统。
- 作者的替代品。
- 可发表质量的保证。
- 长上下文问题的魔法解。

## 界面

应用在本地运行，用浏览器打开。

主流程按以下阶段组织：

| 阶段 | 用途 |
| ---- | ---- |
| **① 蓝图（Blueprint）** | 开书共创、写作指导、故事种子、当前弧与长期方向 |
| **② 角色（Characters）** | 角色卡、关系、以及每个角色的语言风格规则 |
| **③ 细纲（Outline）** | 逐章详细规划 |
| **④ 章节（Chapters）** | 真正的正文生成与修订 |
| **⑤ 设定库（Knowledge Base）** | 结构化的故事／世界信息 |
| **⑥ 全局状态（Global State）** | 摘要、角色状态与待确认信息 |
| **Jobs** | 后台生成任务与可断点恢复的流程 |

界面有意把**规划**和**写作**分开。

---

## 后台任务与断点恢复

长篇生成往往很耗时。

因此生成任务作为后台 Job 运行，而不是把整个应用卡住。

进程失败或应用重启后，已完成的步骤可以复用，而不必从头再生成一遍。

在使用付费或有速率限制的 LLM API 时，这一点尤其重要。

## 快速开始

### 1. 克隆仓库

```bash
git clone https://github.com/Huaji-Wang/novel-engine.git
cd novel-engine
```

### 2. 创建虚拟环境

```bash
python -m venv .venv
```

Windows：

```bash
.venv\Scripts\activate
```

Linux / macOS：

```bash
source .venv/bin/activate
```

### 3. 安装依赖

```bash
pip install -r requirements.txt
```

### 4. 创建配置文件

Linux / macOS：

```bash
cp config.example.yaml config.yaml
```

Windows：

```powershell
copy config.example.yaml config.yaml
```

编辑 `config.yaml`，配置 **OpenAI 兼容** 的 LLM 提供商：

```yaml
llm:
  providers:
    your_provider:
      api_key: "YOUR_API_KEY"
      enabled: true
```

请按你安装版本所支持的 provider 配置来写。

### 5. 启动应用

```bash
python run.py
```

然后打开：

**http://127.0.0.1:8000**

> **不要提交 `config.yaml`。**
> 里面可能有 API 密钥，且已写入 `.gitignore`。

## 推荐工作流

新开一本书，推荐流程是：

```text
Create Book
    ↓
Co-Creation
    ↓
Confirm Creative Instructions
    ↓
Generate Blueprint
    ↓
Review / Edit Blueprint
    ↓
Generate Chapter Outline
    ↓
Review / Revise Outline
    ↓
Generate Chapter
    ↓
Revise / Polish
    ↓
Author Approval
    ↓
Update Story State
    ↓
Next Chapter
```

也可以跳过共创直接生成蓝图；但故事方向通常会更散，因为模型对你的意图知道得更少。

## 质量门

开源版有意使用相对宽松的质量设置。

默认配置：

```yaml
block_finalize: false
auto_rewrite_on_critical: false
auto_humanize_on_fix: true
```

质量系统主要是**助手**，不是专断的门卫。

质量警告不会自动阻止作者定稿。

你可以为自己的部署配得更严。

## LLM 提供商

`novel-engine` 围绕 **OpenAI 兼容 API** 设计，换提供商不必改掉整套写作流程。

因此可以为不同角色试不同模型。

例如，将来可以这样配：

```text
Planning Agent     → Model A
Writing Agent      → Model B
Revision Agent     → Model C
Quality Agent      → Model D
```

具体用哪套模型策略，有意留给配置。

## 这个项目真正在探索什么

更深一层，`novel-engine` 是在做这样一个实验：

> **长篇创作能否被当成持续的多智能体规划问题，而不是一次 LLM 生成问题？**

小说不只是一串彼此独立生成的章节。

它是一套会变的系统：

```text
Characters
    +
World
    +
Events
    +
Goals
    +
Conflicts
    +
Foreshadowing
    +
Author Decisions
    +
Narrative Direction
```

挑战因此不只是把文笔写得更好。

而是在很长一段时间里，维持一个连贯的**有状态的叙事过程**。

这就是这个项目想探索的问题。
